The App Decides the Tool Set

By Anthony Smith · November 24, 2026

TL;DR: The application decides which tools exist, which arguments they accept, and which can write.

Prompt compliance and tool registration are different checks, and reviews often treat them as one. Prompt compliance asks whether the model was told to stay inside a list, while tool registration asks whether the application built that list for the call. A sentence in the system prompt can name the tools that fit the task. That sentence does not create a function, delete a function, or change what a function is allowed to write.

The position is that the model does not widen that list. It can propose a tool name and a set of arguments. The application matches the name to a tool it registered for this call, validates the arguments against a schema it owns, and runs the handler only if both checks pass. If the name is absent, the application refuses. It does not consult the model about whether the name should be added.

Absence from the call catalog means the tool does not exist for that call. Fluency is not a registration path.

The three decisions the application owns

Existence, arguments, and write permission are separate bounds. Collapsing them into one prompt instruction leaves the runtime able to do more than the task needs. Existence is the catalog built for this actor and this task. A handler that lives in the repository is not automatically a tool on the call. Read tools and write tools are different entries. A call that should only read does not register handlers that mutate state.

Arguments are the second bound. The schema is application code. The handler does not see the raw object from the completion. Extra fields are rejected. An identifier is accepted only if it belongs to the caller's scope. An illustration: a completion that names a status update and supplies an order id is still refused when that update tool was not registered, or when the schema rejects the id.

Write permission is the third bound. A write tool is registered only by an explicit choice for this call. An illustration only: a caller who may read GET /api/orders/4021 does not receive a write tool for that order unless the application registered one.

The OWASP excessive agency note describes the risk of giving an agent functions, permissions, or autonomy beyond what the task needs. The matching control is to reduce those three in the application. A warning in the prompt does not remove a registered write tool.

Dispatch is a lookup, not a negotiation. The application reads the proposed name, finds it in the catalog for this call, and parses arguments with that tool's schema. Unknown names stop there. Invalid arguments stop there. A name that exists in another module, or that appeared in user text, is still unknown if this catalog does not contain it.

The snippet below is an illustration of the control, not a trace from a live system. Unknown names are refused before any handler runs, and write tools are added only when the task and the actor both allow a write.

function catalogForCall(actor, task) {
  const tools = {
    readOrder: { write: false, parse: parseOrderId, run: readOrder },
  };

  if (task.allowsStatusUpdate && actor.canUpdateOrder) {
    tools.updateOrderStatus = {
      write: true,
      parse: parseStatusChange,
      run: updateOrderStatus,
    };
  }

  return tools;
}

function dispatch(catalog, proposal) {
  const tool = catalog[proposal.name];
  if (!tool) {
    return { ok: false, reason: "tool_not_registered" };
  }

  const parsed = tool.parse(proposal.args);
  if (!parsed.ok) {
    return { ok: false, reason: "arguments_rejected" };
  }

  return { ok: true, value: tool.run(parsed.value) };
}

What a design review should find

A review should point at code, not at prompt text. The checks below are the bar. If the only bound is a line in the system prompt, the model can still widen the set the application failed to close.

  1. The catalog for the call is built in application code from the actor and the task. It is not taken from user text or from the completion.
  2. Dispatch resolves the proposed name only inside that catalog. An unknown name is refused. There is no fallback that registers a tool because the model named it.
  3. Each tool carries a schema the application owns. Parsing happens before the handler. Rejected arguments never reach a write.
  4. Write tools are opt-in for the call. A read task does not register handlers that create, update, or delete state.
  5. Handlers that exist elsewhere in the process stay unreachable when this catalog omits them. The refusal reason is a fixed code, not a copy of model text.
Reviewers should find the function that builds the catalog and the function that refuses a name outside it. If those functions are missing, the bound is not implemented.

Prompt compliance still matters. It is not the control that decides which tools exist, which arguments they accept, or which of those tools can write. That control sits in the application. The model proposes. The application refuses anything outside the set it already built.
