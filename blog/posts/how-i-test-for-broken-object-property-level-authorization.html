How I Test for Mass Assignment and Excessive Data Exposure

Most APIs get object level authorization right but completely forget property level controls. A developer validates that you can access invoice 4021, but never checks whether you should see the internal_notes field or be allowed to update is_paid. The API returns every column from the database row or accepts every field from your JSON body without asking which properties this specific user role should touch.

This splits into two related flaws. Excessive data exposure happens on reads when the API returns sensitive properties you should not see. Mass assignment happens on writes when the API accepts properties you should not change. Both stem from the same root cause: treating property access as an afterthought once object access is confirmed.

Why Property Controls Are Invisible

Property level flaws hide because they look correct in normal use. Your frontend only displays safe fields and only sends expected parameters, so the API appears to work perfectly. Code review misses it because the authorization check is right there at the top of the function. The reviewer sees the object ID validation and moves on, never noticing that the ORM returns all columns or the update handler binds request data directly to the model. Testing tools that focus on tampering object IDs will never catch a property you were always allowed to read but should not have been shown.

My Testing Method

  1. Capture a legitimate API response for an object you own. Note every property returned, especially metadata fields like created_by, role, status, or anything with internal in the name.
  2. Compare the response schema across different user roles or privilege levels. A low privilege user receiving the same fields as an admin is a finding. Look for PII, financial data, or system fields that should be filtered.
  3. For write operations, capture a normal update request. Add extra properties that exist in the read response but were not in your original payload. Try privilege fields like role, approved, discount_override, or foreign keys like assigned_to.
  4. Test each HTTP verb separately. A GET might filter properties correctly while PATCH accepts everything. POST endpoints that create objects are especially prone to mass assignment since developers focus on happy path fields.
  5. Check for property exposure in error messages and alternative formats. An API might filter JSON responses but leak full objects in XML, CSV exports, or validation errors.
  6. Review any batch or list endpoints separately. Individual object endpoints sometimes have better filtering than collection routes that return arrays of objects.

The Schema Is Not the Contract

A common mistake is assuming your OpenAPI spec or GraphQL schema provides authorization. Schema validation only confirms a field is the right type, not that this user should access it. I have seen APIs with perfect schema validation that leak admin-only properties to every authenticated user because the schema described the database model, not the authorized view. Property level authorization requires explicit allow lists or role based filtering after the schema validates but before the response goes out.

Defensive Implementation

The secure pattern is response shaping and input allow lists at the authorization layer, not the data layer. For reads, define which properties each role can see and filter the response object before serialization. For writes, maintain explicit allow lists of properties each role can modify and reject any fields not on that list.

function filterInvoiceResponse(invoice, userRole) {
  const baseFields = ['id', 'amount', 'date', 'status'];
  const customerFields = [...baseFields, 'items'];
  const adminFields = [...customerFields, 'internal_notes', 'cost', 'margin'];
  
  const allowedFields = userRole === 'admin' ? adminFields : customerFields;
  
  return Object.keys(invoice)
    .filter(key => allowedFields.includes(key))
    .reduce((obj, key) => ({ ...obj, [key]: invoice[key] }), {});
}

Why This Persists

Property level authorization stays broken because it requires more work than object level checks and breaks silently. Developers add one authorization guard at the route level and consider the endpoint secure. ORMs and serializers make it trivial to return entire objects, and explicit property filtering feels like unnecessary overhead when the frontend only uses safe fields anyway. Unlike broken object authorization, where a user sees data that clearly belongs to someone else, property exposure often looks like a feature until someone notices the admin panel fields in the customer API response.

Property level authorization is object level authorization applied one layer deeper. Every field is a decision, not a default.
