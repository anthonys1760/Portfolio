Person Approval Before Write or Send

By Anthony Smith · November 26, 2026

TL;DR: A state-changing tool call waits for a person.

A state-changing tool call waits for a person. The model can propose the action, and it cannot confirm it.

The boundary belongs to the code that performs the tool. A proposal is untrusted data from the model. Approval is a separate record a person creates for that exact call. Until the record exists and matches, the application refuses the write, the send, the delete, and every other state change.

OWASP names the surrounding risk LLM06:2025 Excessive Agency: a model is allowed to act beyond what a person approved. Naming the risk is not the control. The control is a hard wait in the executor, with no path that lets model text stand in for a person.

The four mistakes below are ways that wait gets skipped or aimed at the wrong boundary. They are defense errors, not an ordered method and not steps for attacking a system. Every example in this post is an illustration, not something that happened.

Before any tool runs, the application checks four facts:

  • The tool is classified as read-only or state-changing.
  • A state-changing call carries a person approval record, not a model flag.
  • The approval names the same tool and the same argument hash the person saw.
  • No side effect has started. The call is still a proposal.

Confirmation read from model text

Reading confirmation from the same channel that proposed the action points the control at model output. The fix is to ignore that output. The application does not parse the transcript for a yes, does not honor a consent field on the tool call, and does not treat a system reminder the model can quote as a signature. Approval arrives on a channel the model cannot invoke: a person control bound to an authenticated session, stored as its own record. As an illustration, chat text that says the message may be sent does not authorize the mail tool. The executor still refuses.

The gate left in the chat UI

Rendering a confirm button in the chat UI points the control at the wrong boundary. The button is a view. The side effect lives in the tool runner. If that runner executes whenever a tool call object appears, a missing dialog is only a missing picture. The fix is to refuse inside the runner. No person record means no invocation, including when another service calls the same function. The application does not write, send, or delete and then ask whether that was acceptable.

The function below is an illustration of the check the application owns. It refuses an unclassified tool, a missing person, and a hash that does not match. It is not a log from a running system.

function executeTool(call, approval) {
  const effect = classify(call.name);
  if (effect === "unknown") {
    return refuse("unclassified_tool");
  }
  if (effect === "read_only") {
    return runReadOnly(call);
  }
  if (!approval || approval.actor !== "person") {
    return refuse("person_required");
  }
  if (approval.tool !== call.name || approval.callHash !== hashCall(call)) {
    return refuse("approval_mismatch");
  }
  return runApproved(call);
}

A single tool name as the boundary

Wrapping a single tool name leaves every other mutation ungated. Publish, transfer, delete, comment, and file write share that class when they change state. The fix is to classify at registration, before the model can choose a name. State-changing tools share one person gate. Read-only tools may proceed without it. A tool with no class is refused, not defaulted to safe. As an illustration, treat a call shaped like POST /api/orders/4021 as a write because it changes state, even when the tool name sounds like a read. That path is an illustration of the rule, not a live route.

One approval reused after the call changes

Storing a bare boolean for the conversation lets a later call inherit an earlier yes. The person approved one proposal. A changed recipient, body, amount, path, or tool is a different proposal. The fix is to bind the record to the tool name and a hash of the arguments shown to the person. On mismatch, the application refuses and shows the new proposal. It does not stretch the old record to fit. As an illustration, approval to save a draft to one address does not confirm a send to a second address, even in the same thread.

The model may propose. A person confirms. The application refuses the state change until those roles stay apart.
